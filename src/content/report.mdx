## Question

Agent benchmarks usually assume tools that answer quickly, correctly and honestly. Production tools time out, rate-limit, return stale or contradictory data, fail silently, and pass along text written by untrusted people. **How much does agent performance degrade under these faults, and which faults does an agent handle badly?**

## Methodology

- **Agent.** Claude Haiku 5.5 as a ReAct agent, run through UK AISI's Inspect at reasoning effort _medium_. It works from a written support handbook for Nordlys Supply, a fictional shop, and the same handbook is used in every run. The handbook does not mention prompt injection.
- **Environment.** A simulated order-support desk: 20 tasks across 5 categories and 9 tools. The tools and the world state (orders, payments, refunds, tickets, customers, carrier records) are simulated; the agent is real.
- **Faults.** Seven fault types plus a baseline, injected by a seeded layer between the agent and its tools. The seed fixes which tool is hit and how, so every run meets the same fault again. A fault reaches the agent only if it calls the targeted tool; in this trial that happened in <Exposure /> of fault runs.
- **Design.** <DatasetScale />.
- **Seeds are repeated trials.** The model's outputs cannot be pinned (these models take no temperature setting), so the same run can play out differently. Repeating each setting gives intervals that capture that variation. This trial has one seed per setting.
- **Grading.** Deterministic graders judge the final world state and the call log in code; there are no LLM judges. Replies are judged by their structured `decision` and stated status, and disclosure by an exact match against private values. Each grader is tagged _task_ or _safety_; any failed safety grader makes the run _unsafe_.
- **Frozen setup.** The handbook, tasks, faults and graders were frozen at commit `9e405eb` after a smoke test and a first pass, which found and fixed harness and grading bugs. Nothing was changed to make the results more or less interesting. The bugs and fixes are listed in the trial's review notes (`datasets/haiku-trial/REVIEW.md`).
- **Traces.** Every step (reasoning, tool call, tool result, world change) is recorded in a versioned JSON format and can be replayed step by step.

## Metrics and uncertainty

Every rate is a share of runs and comes with a 95% Wilson score interval. Wilson behaves well near 0% and 100% and at the small sample sizes here (<CellSize /> runs per matrix cell), where the textbook normal interval collapses or spills outside 0–100%.

```text
CI = ( p̂ + z²/2n ± z·√( p̂(1−p̂)/n + z²/4n² ) ) / ( 1 + z²/n ),  z = 1.96
```

**Recovery rate** is paired by task: of the tasks an agent solved in every baseline run, the share of runs it still solved with the fault on. A paired share stays a proportion, so it gets a Wilson interval like every other rate. A ratio of two success rates would not, and it can exceed 1.

**Escalation correctness** counts a run as correct when the agent escalated exactly when it should have: escalation-policy tasks, unverified account changes, and tasks about an order's state once the agent has seen the order record and the carrier disagree.

## Limitations

- One model and one seed per setting. With 20 runs per cell, intervals are about ±20 points wide, so only large effects are visible.
- One simulated domain. Results may not transfer to coding agents, browsing agents or other tool sets.
- Faults are injected one at a time. Real outages often stack, and combinations are not studied yet.
- The graders trust the reply's structured `decision` field. A hand check of 20 replies found no mismatch between the field and the message, but the check is a sample.
- The tools are simulated, so their responses are cleaner and more uniform than a real backend's.
- The model's internal reasoning is not visible in the replays: Claude's thinking is not returned by default, so traces show tool calls and results, replies, and any text the model writes between tool calls.
